Workshop #2 · The Product Builder Certification

From vibe coding to spec engineering.

Five sessions, one trace, every artifact built live in front of you: spec, build, scorecard, debug log, strip.
5 hours live 5 sessions bring your laptop

§ 01Start here

01

Before the session (20 min): install Claude Code and sign in · install Node.js LTS and git · clone the kit, run claude from its root, and type /spec — seeing it offer to interview you is the whole check.

02

Show up with your laptop. We build everything live.

The trace

Across all five sessions, one trace, claude-progress.txt, accumulates the rationale for every decision. The next session reads it.

One line for the day

The spec is the product; code is the disposable thing you regenerate from it. AI doesn't fail so much as drift — ask it to "find me relevant jobs" and it won't error, it returns stale roles and invented companies without ever saying the ask was underspecified. The cure isn't a better model. It's a spec.

§ 03How the workshop runs

For each session:

01

Type the command or paste the RUN block — /spec, /build, /eval, /surgical-fix, /strip. Either way it reads the same blueprint and lands the same artifact.

02

The skill reads its blueprint in modules/ — the procedure is on disk, never from memory.

03

The artifact lands in app/ and its tile lights up on build-assistant.html. The next session reads it from there.

On the projector

Discipline

Every artifact appears in front of you. Nothing is shown that hasn't been built live.

Monday morning you open /spec on your own problem.

What the structure teaches

Each session reads the upstream artifact and produces the artifact the next session will read. The build reads the spec directly; the judge is never the builder; the strip cuts only what the traces prove. Each artifact is the only handoff that crosses session boundaries: the discipline lives in that handoff.

02 · The five sessions

What each session teaches, and why.

Each card carries what the session teaches alongside why the pattern works.
S1

Spec — Working Backwards

interview → write
Session blueprint

Two steps. First the AI interviews you — one topic at a time, probing the soft spots (who has the problem, the pain today, what "good" looks like, then the edges and constraints you haven't thought through) — and it won't write until the problem is sharp, solution-free, every fuzzy word pinned, and you've confirmed it. Then it writes the seven-part spec: the problem, what good looks like, inputs & interfaces, out of scope, the task breakdown, the acceptance checks, and the tech stack. You walk out with a spec the build reads verbatim, the CLAUDE.md that primes every future session, and the checks in evals.md the app will be measured against.

Why this pattern ·Work backwards from the customer, not the solution

Working Backwards is the front half — the promise and the hard questions. The engineering back half — the task breakdown, the acceptance checks, the tech stack — is what makes the spec buildable. Skip either half and it stops being spec engineering. The one-shot /ambiguity-audit then reads the finished spec as an independent critic: names used before they're defined, instructions with no how, numbers with no bound, adjectives with no measure — each with a price tag for what it would cost if it reached the build.

S2

Build

three single-responsibility subagents on one harness
Session blueprint

Three subagents, reading the spec directly: decompose → initialize → write the code. The first translates the spec's Task decomposition into discrete buildable features — it never invents one. The second pins the shared foundation from the spec's Tech stack and Inputs & interfaces (one database, one auth path, one design system) and halts at the credential checkpoint if a needed key is missing — the key goes into .env (gitignored), never pasted into the chat, never written into any other file, and the build never starts half-wired. The third writes one feature at a time, draws every screen with the frontend-design skill from the spec's "what good looks like", reads your dashboard comments before each feature, and writes a RATIONALE entry per feature. You walk out with a running app and a trace that names which feature owns which decision.

Checkpoints: Credential, Comment, Question — blocking conditions that halt the build. And three changes are one-way doors that need a written reason first: inventing a feature with no spec task, using a tech choice not in the config, marking a feature done with no trace line. Everything else rolls back free.

Why this pattern ·Three single-responsibility prompts on one harness

Anthropic's Planner / Generator / Evaluator framing. The workshop maps the decompose and initialize steps to the Planner role (split for traceability), the coding step to the Generator, and S3's independent judge to the Evaluator. The full three-prompt harness runs ~20× the tokens of a single-chat build (Anthropic: ~$200 vs ~$9 for representative tasks). The justification is durability across context resets and per-feature traceability into S3's failed checks, not raw capability.

Principle

Find the simplest solution possible, and only increase complexity when needed. The decompose step is the workshop's complexity addition, kept while debugging in S4 needs per-feature granularity, stripped in S5 if a future model handles whole-app builds reliably.

S3

Eval

independent judge (cross-session split)
Session blueprint

Two passes. Top-down: the build faces the bar-raiser panel's five reviewer dimensions — QA · Architect · Security · Customer sense · Data/accuracy — each raising its one hard question. The checks come from evals.md (you wrote them in S1), each encoded as code (a count, regex, or status code decides it — always preferred) or judge (meaning has to be interpreted; the judge gets two worked examples), and each owned by a reviewer — a reviewer with zero checks is a blind spot the eval flags. A fresh, independent pass grades every check binary: pass / fail / can't-tell — and a row that fails a hard check can't pass anything else. Bottom-up: the traces show what the spec never imagined — you read the failures yourself and note the first thing that went wrong (the root cause, not the cascade; observations, not explanations), the notes cluster into patterns, and every pattern exits one of three doors: fix the obvious, spec the repeating, log the rest. The dashboard carries both passes — scorecard · traces · patterns · actions — with a run-over-run strip where each fix visibly flips a light.

Why this pattern ·the judge is a separate inference call

Self-evaluation fails structurally: the same model biases toward favourable scoring of work it just produced. The fix is a separate inference call, not a better prompt. A can't-tell means the spec never pinned it down — a missing number or bound. That's a spec fix and a re-run, not a debug item; the spec is allowed to change as you learn.

Research note
Judge prompts with 3 critique examples land ~15–20% higher human/model agreement than a plain LLM-judge. And honestly: green means the machine-runnable checks came back clean — simulated reviewers aren't real audits. For money, data, or safety, a human still signs off.
S4

Debug

Surgical Fix · one change at the named layer
Session blueprint

For each failed check: locate it first — M1 trace → M2 feature → M3 commit → M4 file:line (M5 read-back, human-reported bugs only) — then name the layer (spec · screen · tech stack · prompt · data · code), make one targeted change, re-run every check, log the before/after. One change per entry. If the layer is ambiguous, /deep-dive surfaces it. You walk out with debug-log.html, one receipt per fix — tokens, model, and cost for AI fixes; files and lines for code edits — and a prototype that passes the bar.

Why this pattern ·Surgical Fix as the spec-engineer's discipline

Debug is the standout that separates spec engineering from vibe coding. Vibe-coders sweep plausible changes and hope. Spec engineers run NAME → MAKE → RE-RUN → VERIFY → LOG and show the receipts.

Every component in a harness encodes an assumption about what the model can't do on its own. The layer you fix is the assumption you're correcting.

Anthropic harness research
S5

Strip

Model Recall + Strip discipline
Session blueprint

A new model launch fires a Model Recall on your harness. For each piece of scaffolding (pre-baked lookups, extra validation passes, UI scaffolding, prompt workarounds), the trace tells you whether the new model still needs it: does the trace show it firing, did it ever catch a failed check, did any fix touch it, does the build go red without it. Evidence per scaffold, a proposed call per card, then your sign-off at the review checkpoint — the agent never strips on its own. Cap around four strips a session; depth per scaffold beats a long list. You walk out with a leaner harness and the discipline to do this every time a new model ships.

Why this pattern ·Strip with traces, not hope

Harnesses encode assumptions that go stale as models improve.

Anthropic Managed Agents

Canonical example: Sonnet 4.5 had "context anxiety", wrapping tasks up prematurely as it sensed the context limit. Resets were added. Same harness on Opus 4.5 → behavior gone → resets became dead weight. Counter-discipline from Willison's March 2026 Claude Code postmortem: harness "improvements" caused real regressions.

Discipline

Strip because you ran traces, not because a model shipped.

03 · Reference & receipts

Reading list, receipts, and disciplines.

Why-it-matters notes, the anti-pattern that breaks decomposition, and every source the workshop is built on.

§ 01Receipts: accountability for every fix

Every entry in debug-log.html carries a receipt. For AI fixes: input tokens · output tokens · model name · approximate cost in dollars. For plain code edits: the files and lines touched. No receipts means no accountability, and that is the vibe-coding failure mode.

Rule

Show the receipt.

Rendering artifacts
Every HTML artifact carries the five-stage strip (S1 spec → S2 build → S3 eval → S4 debug → S5 strip) in its header. Only app/spec.html carries the selection annotator — select any text, a popover posts your note anchored to that passage, and the build folds it in; every other artifact is a read-only review surface. Artifacts are rendered via the frontend-design skill, never hand-rolled.

§ 02Anti-pattern: don't skip decomposition

A coding step that reads only app-spec.json (the config) without feature-list.json builds the whole app in one pass. The trace can't then tell you which feature regressed when a check fails in S3, and S4's Surgical Fix has nowhere to land.

When a check fails in S3, open claude-progress.txt and look for the entry whose RATIONALE explains the failure path. If the trace doesn't surface the cause, it was too thin. Invoke /deep-dive on the fuzzy incident; the output appends to the trace.

§ 04Disciplines the workshop borrows from

Amazon disciplines

  • Working Backwards + PR-FAQ: the FAQ-as-why. Used in S1.
  • Bar Raiser: 4-evaluator parallel discipline from Amazon hiring. Adapted as the ad-hoc /bar-raiser tool, invoked when a doc needs a harder critique before it ships.
  • Two-way doors: Amazon decision discipline. Used to label every change in the S2 build as reversible or not.

Other disciplines the workshop draws on

  • Antecedent basis discipline: every entity defined before it's referenced; every "the agent shall X" specifies the corresponding HOW. Drives the ambiguity audit in S1 and the screens named in the spec's "what good looks like".
  • 5-Whys / orchestrator-workers pattern: Workshop #1 carryover, reused as /deep-dive. Invoked in S3, S4, S5 when a layer is ambiguous.
  • HTML-over-Markdown for plans / reviews / artifacts: Claude Code default for long structured outputs across S1–S5.

§ 05Workshop-original techniques

These are named or operationalized inside the workshop and don't have an external primary source:

  • Ambiguity Audit: operationalization of antecedent basis as a spec drill. Workshop-coined branding for §112-style rigor.
  • Black Box (Trace Log): naming convention applied to claude-progress.txt + git log. The discipline of reading the trace after incidents (not just recording) is the workshop's framing.
  • Surgical Fix: the one change, one re-eval, one verification discipline is workshop-coined.
  • Model Recall: auto-recall analogy for AI model launches is workshop-coined.

04 · The other half of the workshop

Context Discipline.

The smaller the working context, the sharper Claude gets. Treat the context window as a budget you spend, not a vault you fill.

Pattern: the smaller the working context, the sharper Claude gets. Treat the context window as a budget you spend, not a vault you fill. Every file read, every retry, every dangling MCP server is a withdrawal, and the bill comes due as forgotten instructions, slower turns, and confidently wrong code.

Apply this during every session. The build that ran slowest in the room was usually the one with the heaviest context, not the hardest problem.

§ 01Why context bloat shows up as slowness

Two things happen as the context window fills.

EffectWhat you observe
Latency rises. Each turn re-ingests the full conversation. Once Claude is parsing tens of thousands of tokens before generating the next reply, every interaction feels slower. Spinner sits longer. Replies arrive in pieces.
Quality degrades. Long context dilutes attention. Claude starts ignoring earlier instructions, repeating itself, or "forgetting" a tenet you wrote in CLAUDE.md three turns ago. "Why did it skip the eval step?" "Why is it re-reading the file we already discussed?"

LLMs have an "attention budget" that they draw on when parsing large volumes of context.

Anthropic Engineering

The model has n² pairwise attention relationships across n tokens, and at large n those relationships get stretched thin. Independent research on Claude Opus 4.6 with the 1M-token window shows self-reported degradation starting around 40% utilisation, with restart recommended by 48%. Long before the bar fills, you are paying a tax.

The fix

The fix is not a bigger window. It is keeping the window short.

§ 02How the window fills, even before you type

A fresh Claude Code session in VS Code starts at roughly 7,000–8,000 tokens before your first prompt. The auto-loaded payload, per Anthropic's /context simulator:

The math

The build that read 20 files to chase a bug spent 30,000+ tokens before writing a line of code. The build that asked one targeted question and read one file spent 2,000.

§ 03Diagnosis: know you're in trouble

Run /context in any Claude Code session. It visualises the window and surfaces optimisation tips. Treat the 40% line as a warning, 60% as the redirect signal, and 75% as compact-or-clear immediately.

SymptomLikely cause
Claude re-asks something you answered earlier in the sessionContext past 50%; relevant tokens drowned by noise
Claude ignores a CLAUDE.md tenet it followed at session startCLAUDE.md too long, or context full enough that the rule lost attention weight
Two corrections in a row on the same pointContext polluted with the failed approaches. Stop correcting. /clear and restart with a sharper prompt.
Turns getting visibly slowerToken count crossed the latency threshold for your model
Claude proposes something already rejected in this sessionCompaction has happened and dropped the rejection

The kitchen sink session. You start with one task, then ask Claude something unrelated, then go back to the first task. Context is full of irrelevant information.

§ 04The five disciplines

Clear and compact on purpose, not by accident

/compact runs automatically when you near the limit. By then it is too late: the summary is built from polluted context.

CommandWhen
/clearBetween unrelated tasks. Fresh window. Default to this when starting a new session module.
/compact <instructions>Mid-task, when you want to keep going but the window is full. Pass instructions: "Focus on the spec and the failing eval rows. Drop file-read summaries."
Esc + Esc / /rewindSurgical. Roll back conversation or code to a specific checkpoint. Use after a failed approach.
/btwSidebar questions. The answer appears in an overlay and never enters history.
Rule

If you have corrected Claude twice on the same point, /clear is faster than the third correction.

Delegate reading to subagents

A subagent runs in its own context window. It reads 20 files, returns a 400-token summary, and your main window only pays the summary.

Receipt

Anthropic's own example: subagent read 6,100 tokens of files, returned 420 tokens to the parent.

Use the Explore subagent (or any custom subagent in .claude/agents/) for:

  • Mapping unfamiliar code
  • Finding "where is X defined / which files reference Y"
  • Any investigation that would read 3+ files

Don't use it for:

  • Small targeted lookups where you know the file
  • Anything requiring write access (subagents return text; they don't keep state)

If a task touches more than about five files, it's probably worth isolating in a subagent.

Anthropic docs · rule of thumb

Skills, not bloated CLAUDE.md

Skills load only descriptions (~450 tokens for all of them) at startup. The full skill content loads only when invoked. CLAUDE.md, by contrast, loads in full every session.

Put in CLAUDE.mdPut in a skill
Rules that apply to every taskWorkflows used sometimes
Build / test commands Claude can't guessLong multi-step procedures (eval-blueprint, surgical-fix)
Architectural decisionsDomain knowledge needed only for specific feature work

For each line, ask: Would removing this cause Claude to make mistakes? If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions.

Anthropic on CLAUDE.md hygiene

Skills with disable-model-invocation: true in frontmatter cost zero context until you call them with /<name>. Use this for commit, deploy, send-message, or any skill with side effects.

Plan first, then execute in a fresh session

The workflow in WS2's modules (S1 spec → S2 build → S3 eval → S4 debug → S5 strip) is itself context discipline in action: each session has a clean window and a single artifact.

When you escalate mid-build:

01

Finish the current thought

02

Write the current state to the trace (claude-progress.txt) and CLAUDE.md

03

/clear

04

Start the next module with Read @app/<artifact>, so Claude picks up from disk, not from chat history

Spec-then-execute (Anthropic's recommended pattern) compresses what would be 50 turns of conversation into a 200-line file. The next session starts with a clean window and the spec, not the debate that produced it.

Read narrow, never wide

HabitCost
Read auth.ts (whole file)2,400 tokens
Read auth.ts with offset + limit300 tokens
Glob **/*.ts then Read each15,000+ tokens
Grep "refreshToken"600 tokens, usually enough

When prompting:

  • Be specific: "the bug in auth.ts line ~80" not "the auth bug"
  • Reference files with @path so Claude reads exactly what you mean
  • Allowlist gh, git, bq, etc. so Claude uses CLI tools (one structured line) instead of MCP tools (full schema)

§ 05The VS Code tax, and how to spend less

Running Claude Code as the VS Code extension carries one specific cost the terminal CLI does not: every prompt re-injects your current IDE selection and active file path as <ide_selection> context. Convenient when you mean it. Expensive when you don't.

What this means in practice:

HabitOutcome
Leave a 200-line file open and selected while asking Claude something unrelatedThose 200 lines re-inject on every prompt of the session
Click into a file just to look at it, then promptThat file enters context as "the user selected lines X to Y", and Claude treats it as relevant
Use VS Code's outline/explorer instead of the editor while promptingNo selection re-injection
Practical step

Close or deselect files before prompting on a different topic. Treat the editor cursor as part of your prompt. If you want a clean slate, also /clear. The selection re-injects, but the rest of the window resets.

To block a specific file (e.g. .env) from ever reaching context via the IDE selection, add a Read deny rule for its path in .claude/settings.json.

Note
A setting to disable IDE-selection auto-injection has been requested but is not shipped as of this writing. Track the request at anthropics/claude-code#20944.

§ 06Workshop default: the four-line rule

For every WS2 session (S1 through S5), the default discipline is:

01

/clear at the start of each new module. Do not carry S2 chat into S3.

02

Read the artifact, not the history. Read @app/spec.html beats "remember what we agreed in S1?".

03

Delegate any 3+ file investigation to an Explore subagent.

04

Run /context once per session. If you cross 50% before you have output, stop and ask why.

The student whose build was slowest is rarely the one whose problem was hardest. It is usually the one whose context was heaviest: same model, same machine, same network, half the attention budget left.

§ 07Close-out

  • Append a one-line RATIONALE entry to claude-progress.txt: <ISO timestamp> context <symptom> <fix> (e.g., "/clear after 2 corrections on token bug; restart with spec ref")
  • If a CLAUDE.md tenet got ignored because the file is too long, prune the tenet that no longer earns its line.
