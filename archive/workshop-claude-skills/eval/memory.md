# Memory — eval skill

One line per lesson, newest first, cap ~12. Read before running; append after any
session that taught something — especially judge mistakes, check phrasings that
turned out ambiguous, and failure patterns the checks missed. Prune as you
append: a lesson that has held for 3+ sessions moves into evals.md (if checkable)
or the blueprint (if procedural) and gets deleted here; merge duplicates; delete
entries about behavior that no longer happens.

- An all-green scorecard can sit next to a starved list. The spec's checks all guarded honesty (no padding, real quotes, a gap each) but none set a **recall floor** or a **mode-word-safety** guard — so 4 results and 0-on-"remote" both passed. When Pass 1 comes back clean, push harder on Pass 2 customer-sense: "would the person accept *this few* rows?" is a check, not a vibe.
- "Can't-tell" is coverage, not credit — a single happy run couldn't exercise the remote-surfaces / Manchester-drop / credential-halt scenarios. Grade code-verifiable invariants from the source, and mark the rest can't-tell rather than passing them on a run that never hit the case.
- Diagnose the funnel with real numbers before proposing fixes — the fetch→extract→locate→judge→rank counts (50→32→4; and 50→3 when "remote" is in the ask) named the three clusters far more precisely than reading code could. Reproduce the user's exact two searches first.
